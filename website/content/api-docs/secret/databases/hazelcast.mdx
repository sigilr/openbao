# Hazelcast database plugin HTTP API

The Hazelcast database plugin is one of the supported plugins for the
database secrets engine. Unlike the SQL-style plugins, Hazelcast
open-source has no runtime user-management API — authentication is
configured in the member XML `<security>` block at cluster startup — so
this plugin does not issue dynamic credentials. Instead it lets OpenBao
track and rotate the value of a statically-provisioned credential; see
[Static Roles](/docs/secrets/databases#static-roles) and the [Hazelcast
database secrets engine](pathname:///docs/secrets/databases/hazelcast) docs
page for the full picture.

## Configure connection

In addition to the parameters defined by the [Database
Secrets Engine](index.mdx#configure-connection), this plugin
has a number of parameters to further configure a connection.

| Method | Path                     |
| :----- | :----------------------- |
| `POST` | `/database/config/:name` |

### Parameters

- `url` `(string: <required>)` – Specifies the base URL of the Hazelcast
  REST endpoint used for the reachability check (e.g.
  `http://hazelcast.example.com:5701`).

- `username` `(string: "")` – Specifies the username sent as HTTP Basic
  Auth credentials when calling the Hazelcast REST endpoint's
  `/hazelcast/health/ready` healthcheck path.

- `password` `(string: "")` – Specifies the password corresponding to
  `username`.

- `ca_cert` `(string: "")` – Specifies a PEM-encoded CA certificate (or
  bundle) used to validate the Hazelcast REST endpoint's TLS certificate.

- `ca_path` `(string: "")` – Specifies a filesystem path, on the host
  running the plugin, to a PEM-encoded CA certificate (or bundle) used to
  validate the Hazelcast REST endpoint's TLS certificate.

- `client_cert` `(string: "")` – Specifies a PEM-encoded client certificate
  to present for mTLS to the Hazelcast REST endpoint. Must be set together
  with `client_key`.

- `client_key` `(string: "")` – Specifies the PEM-encoded private key
  corresponding to `client_cert`. Must be set together with `client_cert`.

- `insecure` `(bool: false)` – Skips verification of the Hazelcast REST
  endpoint's TLS certificate when connecting. Intended for development
  only.

This plugin does not accept `username_template` — Hazelcast credentials are
tracked under the literal `username` configured on a static role, and this
plugin does not generate its own usernames.

### Sample payload

```json
{
  "plugin_name": "hazelcast-database-plugin",
  "allowed_roles": "app",
  "url": "http://hazelcast.example.com:5701",
  "username": "admin",
  "password": "admin"
}
```

### Sample request

```shell-session
$ curl \
    --header "X-Vault-Token: ..." \
    --request POST \
    --data @payload.json \
    http://127.0.0.1:8200/v1/database/config/hazelcast
```

## Statements

Hazelcast has no dynamic-user statement language usable by this plugin —
open-source Hazelcast has no runtime user-management API at all, and even
Enterprise's `ClusterPermissionsConfig` API is not driven by
statement-style input. As a result the plugin does not read or use
`creation_statements`, `revocation_statements`, `rollback_statements`, or
`root_rotation_statements` at all; any value supplied for these fields is
accepted by the database secrets engine framework but ignored.

- Dynamic roles (`bao write database/roles/:name` followed by
  `bao read database/creds/:name`) are **not supported**. Creating a
  dynamic role succeeds, but reading credentials from it always fails with:

  ```text
  dynamic credentials are not supported by Hazelcast OSS (auth is
  configured in member XML at startup); use static-roles to track a
  manually-provisioned credential, or run a sidecar that updates the
  cluster config on UpdateUser
  ```

- Static roles are the supported credential-tracking mechanism. Configure
  one with a `username` that already exists in the member XML security
  realm, and a `rotation_period`:

  ```shell-session
  $ bao write database/static-roles/app \
      db_name=hazelcast \
      username=app \
      rotation_period=24h
  ```

  On each rotation OpenBao generates a new password and stores it — it
  does not push the value to the Hazelcast cluster. An external system
  must apply the same password to the member XML security realm (or,
  on Enterprise, the `ClusterPermissionsConfig` API) backing that
  credential, typically followed by a rolling restart, to keep it in sync.

- Root credential rotation (`bao write -force database/rotate-root/:name`)
  behaves the same way: OpenBao generates and stores a new root
  `username`/`password` pair in the connection configuration without
  contacting the cluster.
