# DocumentDB database plugin HTTP API

The DocumentDB database plugin is one of the supported plugins for the database
secrets engine. This plugin generates database credentials dynamically based on
configured roles against the [open-source DocumentDB
engine](https://github.com/documentdb/documentdb)'s MongoDB-compatible
gateway. It is **not** for the AWS-managed "Amazon DocumentDB" service.

## Configure connection

In addition to the parameters defined by the [Database
Backend](index.mdx#configure-connection), this plugin
has a number of parameters to further configure a connection.

| Method | Path                     |
| :----- | :----------------------- |
| `POST` | `/database/config/:name` |

### Parameters

- `connection_url` `(string: <required>)` – Specifies the MongoDB-style
  connection URI for the DocumentDB gateway, e.g.
  `mongodb://{{username}}:{{password}}@host:10260/?tls=true`. The gateway
  process typically listens on port `10260`. This field can be templated and
  supports passing the `username` and `password` parameters in the
  `{{field_name}}` format. A templated connection URL is required when using
  root credential rotation.

- `username` `(string: <required>)` – Specifies the root credential username
  OpenBao uses to log into the gateway and issue/revoke dynamic users.

- `password` `(string: <required>)` – Specifies the root credential password
  corresponding to `username`.

- `tls_ca` `(string: "")` – Specifies a PEM bundle containing one or more
  custom CA certificates to trust when connecting to the gateway, e.g. for
  the upstream docker quickstart's self-signed certificate.

- `tls_ca_path` `(string: "")` – Specifies a filesystem path to a PEM bundle
  containing one or more custom CA certificates to trust, as an alternative
  to inlining the PEM contents via `tls_ca`.

- `insecure` `(bool: false)` – Skips TLS certificate verification. Intended
  for development clusters only — pairs with the upstream docker
  quickstart's self-signed gateway certificate. Do not use in production.

- `connect_timeout` `(string: "1m")` – Specifies how long the driver waits
  when establishing a new connection before timing out.

- `socket_timeout` `(string: "1m")` – Specifies how long the driver waits for
  a socket read or write to complete before timing out.

- `server_selection_timeout` `(string: "")` – Specifies how long the driver
  waits when selecting a server for an operation before timing out. If
  unset, the underlying MongoDB driver's default is used.

- `username_template` `(string)` - [Template](/docs/concepts/username-templating) describing how
  dynamic usernames are generated.

<details>
<summary><b>Default Username Template</b></summary>

```
{{ printf "v-%s-%s-%s-%s" (.DisplayName | truncate 15) (.RoleName | truncate 15) (random 20) (unix_time) | replace "." "-" | truncate 100 }}
```

<details>
<summary><b>Example Usernames:</b></summary>

| Example       |                                                        |
| ------------- | ------------------------------------------------------ |
| `DisplayName` | `token`                                                 |
| `RoleName`    | `myrolename`                                            |
| Username      | `v-token-myrolename-uszt1n4cyhal4m0xtgx3-1614294836`    |

</details>
</details>

TLS is always negotiated for connections made by this plugin — the driver's
TLS configuration is always set (minimum TLS 1.2), regardless of whether
`connection_url` includes `tls=true`. There is no option to run this plugin
over a plaintext connection.

### Sample payload

```json
{
  "plugin_name": "documentdb-database-plugin",
  "allowed_roles": "reader",
  "connection_url": "mongodb://{{username}}:{{password}}@docdb.example.com:10260/?tls=true",
  "username": "documentdb",
  "password": "secret",
  "tls_ca_path": "/etc/openbao/documentdb-ca.pem"
}
```

### Sample request

```shell-session
$ curl \
    --header "X-Vault-Token: ..." \
    --request POST \
    --data @payload.json \
    http://127.0.0.1:8200/v1/database/config/docdb
```

## Statements

Unlike SQL-style database plugins, this plugin does not use
semicolon-separated statement lists. Instead `creation_statements` (and,
optionally, `revocation_statements`) are each a single JSON document
describing the authentication database and role(s) to apply, matching the
shape the gateway's `createUser` command expects — the same shape used by
OpenBao's MongoDB plugin.

For more information on configuring roles see the [Role
API](index.mdx#create-role) in the database secrets engine docs.

### Parameters

The following are the statements used by this plugin. If not mentioned in this
list the plugin does not support that statement type.

- `creation_statements` `(string: <required>)` – Specifies a single JSON
  document describing the user to create:

  ```json
  {
    "db": "admin",
    "roles": [
      { "role": "read", "db": "reports" },
      { "role": "readWrite", "db": "billing" }
    ]
  }
  ```

  - `db` (optional, defaults to `"admin"`) is the authentication database the
    user is created in.
  - `roles` (required) is an array of role documents. Bare role names (no
    `db`) are flattened to plain strings; db-qualified roles are passed
    through as objects, matching `createUser`'s expected shape.

  There is no built-in default; a role without `creation_statements` fails to
  issue credentials.

- `revocation_statements` `(string: "")` – Specifies a single JSON document,
  in the same `{"db": "..."}` shape as `creation_statements`, used to
  determine the authentication database to run `dropUser` against. Only `db`
  is read; if not provided, or if `db` is omitted, defaults to `"admin"`. If
  the user has already been removed, revocation is treated as successful
  rather than retried.

`rollback_statements` and `rotation_statements` are accepted by the database
secrets engine framework but are not used by this plugin — password rotation
for static roles is performed with the gateway's `updateUser` command
directly, not through a configurable statement.

## Root credential rotation

```shell-session
$ bao write -force database/rotate-root/docdb
```

Rotates the root user's password (the `username`/`password` pair configured
on `database/config/:name`) via `updateUser`. The old password is not
recoverable afterward.

## Static roles

Static roles rotate the password of an existing DocumentDB user on a
schedule, via `updateUser`:

```shell-session
$ bao write database/static-roles/svc \
    db_name=docdb \
    username=svc \
    rotation_period=24h
```

The gateway has no native `VALID UNTIL` clause on users, so dynamic-role
lease expiry is enforced by OpenBao revoking the lease (`dropUser`), not by
the database itself.
