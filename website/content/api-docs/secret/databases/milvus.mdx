# Milvus database plugin HTTP API

The Milvus database plugin is one of the supported plugins for the database
secrets engine. This plugin generates database credentials dynamically based
on configured roles against a Milvus 2.x cluster's HTTP RESTful API v2.

## Configure connection

In addition to the parameters defined by the [Database
Secrets Engine](index.mdx#configure-connection), this plugin
has a number of parameters to further configure a connection.

| Method | Path                     |
| :----- | :----------------------- |
| `POST` | `/database/config/:name` |

### Parameters

- `url` `(string: <required>)` – Specifies the Milvus HTTP RESTful API v2
  base URL, e.g. `http://milvus.example.com:19530`. All user/role management
  calls are issued relative to this URL.

- `username` `(string: "")` – Specifies the root credential username OpenBao
  uses to authenticate to Milvus and issue/revoke dynamic users. Required
  unless `token` is set.

- `password` `(string: "")` – Specifies the root credential password
  corresponding to `username`. Required unless `token` is set.

- `token` `(string: "")` – Specifies a bearer API token (Zilliz Cloud style)
  to use instead of `username`/`password`. Sent as `Authorization: Bearer
  <token>` on every request. Either `token`, or both `username` and
  `password`, must be provided.

- `db_name` `(string: "")` – Specifies the Milvus database name to send as
  the `dbName` request header on every call. If unset, no `dbName` header is
  sent and Milvus uses its default database.

- `ca_cert` `(string: "")` – Specifies a PEM-encoded CA certificate (or
  bundle) to use when validating the Milvus server's TLS certificate.

- `ca_path` `(string: "")` – Specifies a filesystem path to a PEM-encoded CA
  certificate (or bundle) to use when validating the Milvus server's TLS
  certificate.

- `client_cert` `(string: "")` – Specifies a PEM-encoded client certificate
  to present for mTLS. Must be set together with `client_key`.

- `client_key` `(string: "")` – Specifies the PEM-encoded private key
  corresponding to `client_cert`. Must be set together with `client_cert`.

- `insecure` `(bool: false)` – Skips TLS certificate verification when
  connecting to Milvus. Intended for development only.

- `username_template` `(string)` - [Template](/docs/concepts/username-templating) describing how
  dynamic usernames are generated. Milvus 2.4+ rejects usernames longer than
  32 characters, so custom templates must stay within that limit.

<details>
<summary><b>Default Username Template</b></summary>

```
{{ printf "v-%s-%s-%s" (.DisplayName | truncate 8) (.RoleName | truncate 8) (random 10) | replace "." "-" | truncate 32 }}
```

<details>
<summary><b>Example Usernames:</b></summary>

| Example       |                             |
| ------------- | --------------------------- |
| `DisplayName` | `token`                     |
| `RoleName`    | `myrolename`                |
| Username      | `v-token-myrolena-uszt1n4cyh` |

### Sample payload

```json
{
  "plugin_name": "milvus-database-plugin",
  "allowed_roles": "reader",
  "url": "http://milvus.example.com:19530",
  "username": "root",
  "password": "Milvus123"
}
```

### Sample request

```shell-session
$ curl \
    --header "X-Vault-Token: ..." \
    --request POST \
    --data @payload.json \
    http://127.0.0.1:8200/v1/database/config/milvus
```

## Statements

Unlike SQL-style database plugins, this plugin does not use
semicolon-separated statement lists. `creation_statements` is a single JSON
document listing pre-existing Milvus role names to grant to the new user. For
more information on configuring roles see the [Role
API](index.mdx#create-role) in the database secrets engine docs.

The following are the statements used by this plugin. If not mentioned in this
list the plugin does not support that statement type.

- `creation_statements` `(string: <required>)` – Specifies a single JSON
  document listing the Milvus roles to grant to the new user:

  ```json
  { "roles": ["public"] }
  ```

  `roles` is an array of bare role name strings that must already exist on
  the cluster; this plugin does not create roles. On the wire the plugin
  issues, in order:

  ```
  POST .../v2/vectordb/users/create      {"userName":"<name>","password":"<password>"}
  POST .../v2/vectordb/users/grant_role  {"userName":"<name>","roleName":"<role>"}   (once per role)
  ```

  If any `grant_role` call fails, the plugin issues `POST
  .../v2/vectordb/users/drop {"userName":"<name>"}` before returning the
  error, so no half-configured user is left behind. There is no built-in
  default; a role without `creation_statements`, or with a
  `creation_statements` that isn't a valid JSON role document, fails to issue
  credentials.

`revocation_statements`, `rollback_statements`, and `root_rotation_statements`
are accepted by the database secrets engine framework but are not used by
this plugin. Revocation always issues `POST .../v2/vectordb/users/drop
{"userName":"<name>"}`. Password rotation, for both root credentials and
static roles, always issues `POST .../v2/vectordb/users/update_password
{"userName":"<name>","newPassword":"<password>"}`.

Milvus returns HTTP 200 with an envelope `{"code": N, "message": "..."}` even
for API-level failures; the plugin parses this envelope and treats a
non-zero `code` as an error on every call above.

## Root credential rotation

```shell-session
$ bao write -force database/rotate-root/milvus
```

Rotates the root user's password (the `username`/`password` pair configured
on `database/config/:name`) via `users/update_password`. The old password is
not recoverable afterward.

## Static roles

Static roles rotate the password of an existing Milvus user on a schedule,
via the same `users/update_password` call:

```shell-session
$ bao write database/static-roles/svc \
    db_name=milvus \
    username=svc \
    rotation_period=24h
```
