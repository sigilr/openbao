# ZooKeeper database secrets engine

Apache ZooKeeper is one of the supported plugins for the database secrets
engine, but it works differently from the SQL-style plugins. ZooKeeper's
SASL/`digest` authentication scheme is just a shared `username:password`
baked into a server-side `jaas.conf` (or a `zoo.cfg` `digest:` entry) at
ensemble startup — it is not a central user registry, and there is no
runtime API to create, update, or delete a principal. ACLs on individual
znodes *can* be reconfigured at runtime, but they are tied to existing
digest principals rather than exposing a dynamic-credential surface.

Instead, `zookeeper-database-plugin` lets OpenBao be the source of truth for
a credential's value and rotation schedule, using [Static
Roles](index.mdx#static-roles) as the only supported workflow:

- `Initialize` (and `VerifyConnection`) optionally check that the configured
  ensemble node is reachable by opening a TCP connection and sending
  ZooKeeper's 4-letter `ruok` command. A healthy node replies `imok`; if the
  ensemble restricts 4-letter-word commands via `4lw.commands.whitelist`,
  the plugin surfaces the empty reply with an actionable hint.
- Dynamic credentials (`bao read database/creds/...`) are **not
  supported**. `NewUser` always returns an explicit error telling the
  operator to use static roles, or run a sidecar that applies the rotated
  value to the ensemble.
- Static-role rotation (`UpdateUser`) does not contact the ZooKeeper
  ensemble at all. It validates the request and returns success so that
  OpenBao tracks the new password and emits the usual audit events, but
  applying that password to the `jaas.conf` / `zoo.cfg` digest entry (and
  any znode ACLs referencing it) — typically followed by a rolling
  restart — is left to an external system, which is out of scope for this
  plugin.
- `DeleteUser` is likewise a no-op against the ensemble.

This is the same shape used by the Memcached, Qdrant, Weaviate, Db2, and
Hazelcast plugins in this repo for servers with no runtime user-management
API.

See the [database secrets engine](index.mdx) docs for more information about
setting up the database secrets engine.

## Capabilities

| Plugin Name                 | Root Credential Rotation | Dynamic Roles | Static Roles | Username Customization |
| ---------------------------- | --------------------------- | ---------------- | --------------- | ------------------------- |
| `zookeeper-database-plugin` | Yes                       | No             | Yes           | No                      |

Both "Root Credential Rotation" and "Static Roles" here are OpenBao-side
bookkeeping only: `bao write -force database/rotate-root/<name>` and
static-role rotation both succeed and update the password OpenBao tracks,
but neither pushes the new password to the ZooKeeper ensemble. An operator
or sidecar must apply the same value to the `jaas.conf` / `zoo.cfg` digest
entry (and any znode ACLs referencing it) backing that credential, followed
by a rolling restart, to keep it in sync. `zookeeper-database-plugin` does
not support `username_template` — usernames are the literal value
configured on the static role.

## Setup

1.  Enable the database secrets engine if it is not already enabled:

    ```shell-session
    $ bao secrets enable database
    Success! Enabled the database secrets engine at: database/
    ```

    By default, the secrets engine will enable at the name of the engine. To
    enable the secrets engine at a different path, use the `-path` argument.

1.  Configure OpenBao with the proper plugin and connection information:

    ```shell-session
    $ bao write database/config/zk \
        plugin_name="zookeeper-database-plugin" \
        address="zookeeper.example.com:2181" \
        allowed_roles="app"
    Success! Data written to: database/config/zk
    ```

1.  Configure a static role that maps a name in OpenBao to a
    manually-provisioned ZooKeeper digest username (an identity already
    present in `jaas.conf` / `zoo.cfg`), and a rotation period for OpenBao to
    generate and track a new password on:

    ```shell-session
    $ bao write database/static-roles/app \
        db_name="zk" \
        username="app" \
        rotation_period="24h"
    Success! Data written to: database/static-roles/app
    ```

    Attempting to create a dynamic role and read `database/creds/<role>`
    against this plugin fails with an explicit "dynamic credentials are not
    supported" error — use static roles as shown above instead.

## Usage

After the secrets engine is configured and a user/machine has an OpenBao
token with the proper permission, it can read the current static
credential.

1.  Read the tracked password from the `/static-creds` endpoint with the
    name of the role:

    ```shell-session
    $ bao read database/static-creds/app
    Key                    Value
    ---                    -----
    last_vault_rotation    2026-08-07T09:00:00.000000000Z
    password               SsnoaA-8Tv4t34f41baD
    rotation_period        24h
    ttl                    23h59m12s
    username               app
    ```

    Apply this password to the `jaas.conf` / `zoo.cfg` digest entry (and any
    znode ACLs referencing it) out of band — for example from a sidecar or
    configuration-management run, followed by a rolling restart — to keep
    the ensemble in sync with OpenBao.
