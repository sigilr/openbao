# Weaviate database secrets engine

Weaviate is one of the supported plugins for the database secrets engine, but
it works differently from the SQL-style plugins. Weaviate self-hosted has
**no runtime key-management API** — API keys are loaded from the
`AUTHENTICATION_APIKEY_ALLOWED_KEYS` environment variable at server startup,
and there is no protocol equivalent to a SQL `CREATE USER`/`GRANT` that this
plugin could call at request time to mint a new, scoped credential.

Instead, `weaviate-database-plugin` lets OpenBao be the source of truth for
the value and rotation schedule of a Weaviate API key, using [Static
Roles](index.mdx#static-roles) as the primary supported workflow:

- `Initialize` (and `VerifyConnection`) call the configured server's
  `/v1/.well-known/ready` endpoint, sending the configured `api_key` as a
  Bearer token, to confirm the server is reachable and (if a key is set)
  that the key is accepted. This is a reachability/health check, not a
  key-provisioning call.
- Dynamic credentials (`bao read database/creds/...`) are **not
  supported**. `NewUser` always returns an explicit error telling the
  operator to use static roles or external configuration management
  instead.
- Static-role rotation (`UpdateUser`) does not contact the Weaviate server
  at all. It validates the request and returns success so that OpenBao
  tracks the new key and emits the usual audit events, but applying that
  key to the server (setting `AUTHENTICATION_APIKEY_ALLOWED_KEYS` and
  restarting/reloading the process) is left to an external system — a
  sidecar or configuration-management tool that watches OpenBao and pushes
  the value — which is out of scope for this plugin.
- `DeleteUser` is likewise a no-op against the server.

See the [database secrets engine](index.mdx) docs for more information about
setting up the database secrets engine.

## Capabilities

| Plugin Name                 | Root Credential Rotation | Dynamic Roles | Static Roles | Username Customization |
| ---------------------------- | --------------------------- | ---------------- | ---------------- | ------------------------- |
| `weaviate-database-plugin`  | Yes                        | No               | Yes             | No                       |

Both "Root Credential Rotation" and "Static Roles" here are OpenBao-side
bookkeeping only: `bao write -force database/rotate-root/<name>` and
static-role rotation both succeed and update the key OpenBao tracks, but
neither pushes the new key to the Weaviate server. An operator or sidecar
must apply the same value to the server (via
`AUTHENTICATION_APIKEY_ALLOWED_KEYS` and a restart/reload) out of band to
keep it in sync. `weaviate-database-plugin` does not support
`username_template` — usernames are the literal value configured on the
static role, and are used only as the OpenBao-side name tracking the key,
not sent to Weaviate.

## Setup

1.  Enable the database secrets engine if it is not already enabled:

    ```shell-session
    $ bao secrets enable database
    Success! Enabled the database secrets engine at: database/
    ```

    By default, the secrets engine will enable at the name of the engine. To
    enable the secrets engine at a different path, use the `-path` argument.

1.  Configure OpenBao with the proper plugin and connection information:

    ```shell-session
    $ bao write database/config/weaviate \
        plugin_name="weaviate-database-plugin" \
        url="https://weaviate.example.com:8080" \
        api_key="topsecret" \
        allowed_roles="app"
    Success! Data written to: database/config/weaviate
    ```

1.  Configure a static role that maps a name in OpenBao to the
    manually-provisioned Weaviate API key, and a rotation period for OpenBao
    to generate and track a new key on:

    ```shell-session
    $ bao write database/static-roles/app \
        db_name="weaviate" \
        username="app" \
        rotation_period="24h"
    Success! Data written to: database/static-roles/app
    ```

    Attempting to create a dynamic role and read `database/creds/<role>`
    against this plugin fails with an explicit "dynamic credentials are not
    supported by Weaviate self-hosted" error — use static roles as shown
    above instead.

## Usage

After the secrets engine is configured and a user/machine has an OpenBao token
with the proper permission, it can read the current static credential.

1.  Read the tracked key from the `/static-creds` endpoint with the name of
    the role:

    ```shell-session
    $ bao read database/static-creds/app
    Key                    Value
    ---                    -----
    last_vault_rotation    2026-08-07T09:00:00.000000000Z
    password               SsnoaA-8Tv4t34f41baD
    rotation_period        24h
    ttl                    23h59m12s
    username               app
    ```

    The value returned in the `password` field is the tracked Weaviate API
    key — it is not a database account password, and the plugin does not
    mint scoped tokens or per-user credentials. Apply this value to the
    Weaviate server's `AUTHENTICATION_APIKEY_ALLOWED_KEYS` configuration out
    of band (for example, from a sidecar or configuration-management run)
    to keep the server in sync with OpenBao.
