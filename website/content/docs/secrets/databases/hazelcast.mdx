# Hazelcast database secrets engine

Hazelcast is one of the supported plugins for the database secrets engine, but
it works differently from the SQL-style plugins. Hazelcast IMDG / Platform
open-source authentication is configured in the member XML `<security>`
block at cluster startup — there is no runtime API to create, update, or
delete cluster users. (Hazelcast Enterprise's `Permissions` API can be
reconfigured at runtime via `ClusterPermissionsConfig`, but the plugin keeps
a uniform surface across editions and treats both as static.)

Instead, `hazelcast-database-plugin` lets OpenBao be the source of truth for
a credential's value and rotation schedule, using [Static
Roles](index.mdx#static-roles) as the only supported workflow:

- `Initialize` (and `VerifyConnection`) optionally ping the configured
  Hazelcast REST endpoint's `/hazelcast/health/ready` path with HTTP Basic
  Auth to confirm the cluster is reachable.
- Dynamic credentials (`bao read database/creds/...`) are **not
  supported**. `NewUser` always returns an explicit error telling the
  operator to use static roles, or run a sidecar that applies the rotated
  value to the cluster.
- Static-role rotation (`UpdateUser`) does not contact the Hazelcast cluster
  at all. It validates the request and returns success so that OpenBao
  tracks the new password and emits the usual audit events, but applying
  that password to the member XML security realm (or, on Enterprise, the
  `ClusterPermissionsConfig` API) is left to an external system — a
  sidecar or configuration-management tool that watches OpenBao and pushes
  the value, followed by a rolling restart if required — which is out of
  scope for this plugin.
- `DeleteUser` is likewise a no-op against the cluster.

This is the same shape used by the Memcached, Qdrant, Weaviate, and Db2
plugins in this repo for servers with no runtime user-management API.

See the [database secrets engine](index.mdx) docs for more information about
setting up the database secrets engine.

## Capabilities

| Plugin Name                | Root Credential Rotation | Dynamic Roles | Static Roles | Username Customization |
| --------------------------- | --------------------------- | ---------------- | --------------- | ------------------------- |
| `hazelcast-database-plugin` | Yes                       | No             | Yes           | No                      |

Both "Root Credential Rotation" and "Static Roles" here are OpenBao-side
bookkeeping only: `bao write -force database/rotate-root/<name>` and
static-role rotation both succeed and update the password OpenBao tracks,
but neither pushes the new password to the Hazelcast cluster. An operator
or sidecar must apply the same value to the member XML security realm (or
Enterprise `ClusterPermissionsConfig`) backing that credential to keep it
in sync. `hazelcast-database-plugin` does not support `username_template`
— usernames are the literal value configured on the static role.

## Setup

1.  Enable the database secrets engine if it is not already enabled:

    ```shell-session
    $ bao secrets enable database
    Success! Enabled the database secrets engine at: database/
    ```

    By default, the secrets engine will enable at the name of the engine. To
    enable the secrets engine at a different path, use the `-path` argument.

1.  Configure OpenBao with the proper plugin and connection information:

    ```shell-session
    $ bao write database/config/hazelcast \
        plugin_name="hazelcast-database-plugin" \
        url="http://hazelcast.example.com:5701" \
        username="admin" \
        password="admin" \
        allowed_roles="app"
    Success! Data written to: database/config/hazelcast
    ```

1.  Configure a static role that maps a name in OpenBao to a
    manually-provisioned Hazelcast username (an identity already present in
    the member XML security realm), and a rotation period for OpenBao to
    generate and track a new password on:

    ```shell-session
    $ bao write database/static-roles/app \
        db_name="hazelcast" \
        username="app" \
        rotation_period="24h"
    Success! Data written to: database/static-roles/app
    ```

    Attempting to create a dynamic role and read `database/creds/<role>`
    against this plugin fails with an explicit "dynamic credentials are not
    supported" error — use static roles as shown above instead.

## Usage

After the secrets engine is configured and a user/machine has an OpenBao
token with the proper permission, it can read the current static
credential.

1.  Read the tracked password from the `/static-creds` endpoint with the
    name of the role:

    ```shell-session
    $ bao read database/static-creds/app
    Key                    Value
    ---                    -----
    last_vault_rotation    2026-08-07T09:00:00.000000000Z
    password               SsnoaA-8Tv4t34f41baD
    rotation_period        24h
    ttl                    23h59m12s
    username               app
    ```

    Apply this password to the Hazelcast member XML security realm (or, on
    Enterprise, the `ClusterPermissionsConfig` API) out of band — for
    example from a sidecar or configuration-management run, followed by a
    rolling restart if required — to keep the cluster in sync with OpenBao.
