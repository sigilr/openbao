# DocumentDB database secrets engine

DocumentDB is one of the supported plugins for the database secrets engine. This
plugin generates dynamic credentials against the
[open-source DocumentDB engine](https://github.com/documentdb/documentdb) — a
PostgreSQL extension that exposes a MongoDB-compatible wire protocol via a
gateway process. It is the same engine that powers Azure Cosmos DB for
MongoDB vCore. Because the gateway speaks the mongo wire protocol, clients
(and this plugin) connect with the official MongoDB driver, and the plugin
also supports [Static Roles](index.mdx#static-roles).

See the [database secrets engine](index.mdx) docs for
more information about setting up the database secrets engine.

:::warning[Not for Amazon DocumentDB]

This plugin targets the **open-source** `documentdb/documentdb` engine, not
the AWS-managed "Amazon DocumentDB" service. The defaults differ from that
managed offering — most notably, this plugin does not force
`retryWrites=false`, since the open-source engine's PostgreSQL-backed
transaction layer supports retryable writes. Because the underlying RBAC and
command surface is whatever the gateway version implements rather than the
full MongoDB feature set, not every MongoDB role or admin command is
guaranteed to be available; consult the upstream DocumentDB docs for the
supported RBAC catalog before writing `creation_statements`.

:::

Unlike the SQL-style database plugins, `creation_statements` is a single JSON
document describing the authentication database and the roles to grant,
rather than a semicolon-separated list of SQL statements — the same shape
used by OpenBao's MongoDB plugin.

## Capabilities

| Plugin Name                 | Root Credential Rotation | Dynamic Roles | Static Roles | Username Customization |
| ---------------------------- | ------------------------ | -------------- | -------------- | ------------------------ |
| `documentdb-database-plugin` | Yes                       | Yes            | Yes            | Yes                      |

## Setup

1.  Enable the database secrets engine if it is not already enabled:

    ```shell-session
    $ bao secrets enable database
    Success! Enabled the database secrets engine at: database/
    ```

    By default, the secrets engine will enable at the name of the engine. To
    enable the secrets engine at a different path, use the `-path` argument.

1.  Configure OpenBao with the proper plugin and connection information. The
    gateway process typically listens on port `10260`:

    ```shell-session
    $ bao write database/config/docdb \
        plugin_name="documentdb-database-plugin" \
        allowed_roles="reader" \
        connection_url="mongodb://{{username}}:{{password}}@docdb.example.com:10260/?tls=true" \
        username="documentdb" \
        password="secret" \
        tls_ca_path="/etc/openbao/documentdb-ca.pem"
    Success! Data written to: database/config/docdb
    ```

    Against the upstream docker quickstart, which presents a self-signed
    gateway certificate, use `insecure=true` instead of `tls_ca_path`:

    ```shell-session
    $ bao write database/config/docdb \
        plugin_name="documentdb-database-plugin" \
        allowed_roles="reader" \
        connection_url="mongodb://{{username}}:{{password}}@localhost:10260/?tls=true" \
        username="documentdb" \
        password="Documentdb_!" \
        insecure="true"
    ```

1.  Configure a role that maps a name in OpenBao to a DocumentDB role document
    to execute to create the database credential:

    ```shell-session
    $ bao write database/roles/reader \
        db_name="docdb" \
        creation_statements='{"db":"admin","roles":[{"role":"read","db":"app"}]}' \
        default_ttl="1h" \
        max_ttl="24h"
    Success! Data written to: database/roles/reader
    ```

    `creation_statements` is a JSON document, not a list of SQL statements:

    - `db` (optional, defaults to `"admin"`) is the authentication database
      the user is created in.
    - `roles` (required) is an array of role documents. Bare role names (no
      `db`) are flattened to plain strings; db-qualified roles are passed
      through as objects — matching what the gateway's `createUser` command
      expects.

## Usage

After the secrets engine is configured and a user/machine has an OpenBao token with
the proper permission, it can generate credentials.

1.  Generate a new credential by reading from the `/creds` endpoint with the name
    of the role:

    ```shell-session
    $ bao read database/creds/reader
    Key                Value
    ---                -----
    lease_id           database/creds/reader/2f6a614c-4aa2-7b19-24b9-ad944a8d4de6
    lease_duration     1h
    lease_renewable    true
    password           Bao-Docdb-1234567890
    username           v-token-reader-3pfw6t8rvmc8mbkz8zef-1717000000
    ```

## DocumentDB-specific notes

- **TLS is always negotiated**: this plugin always configures a TLS client
  (minimum TLS 1.2), so connections are made over TLS regardless of whether
  `connection_url` includes `tls=true`. There is no way to run this plugin
  over a plaintext connection. Use `tls_ca` / `tls_ca_path` to trust a custom
  CA bundle — e.g. the upstream docker quickstart's self-signed gateway
  cert — or `insecure=true` to skip certificate verification entirely.
  `insecure=true` is intended for development clusters only; never use it
  against a production gateway.
- **No forced `retryWrites=false`**: unlike the AWS-managed Amazon
  DocumentDB service, the open-source engine supports retryable writes, so
  the plugin leaves the driver's default in place. If an older gateway
  version rejects retryable writes, disable them explicitly with
  `?retryWrites=false` in `connection_url`.
- **Static roles and password rotation**: password rotation for both root
  credentials and static roles is performed with the gateway's `updateUser`
  command. The gateway has no native `VALID UNTIL` on users, so lease expiry
  for *dynamic* roles is enforced purely by OpenBao revoking the lease
  (`DeleteUser` / `dropUser`), not by the database itself. A user that no
  longer exists at revocation time is treated as a successful revoke.
