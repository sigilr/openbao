# Milvus database secrets engine

Milvus is one of the supported plugins for the database secrets engine. This
plugin generates dynamic credentials against a
[Milvus](https://milvus.io/) 2.x cluster via its HTTP RESTful API v2
(`/v2/vectordb/users/...`). It also supports [Static
Roles](index.mdx#static-roles).

See the [database secrets engine](index.mdx) docs for
more information about setting up the database secrets engine.

Unlike the SQL-style database plugins, `creation_statements` is a single JSON
document listing pre-existing Milvus role names to grant to the new user,
rather than a semicolon-separated list of statements. Under the hood the
plugin creates the user (`POST .../v2/vectordb/users/create`) and then grants
each listed role (`POST .../v2/vectordb/users/grant_role`). The roles
referenced by `creation_statements` must already exist on the cluster — this
plugin does not create roles, only users and role grants. Milvus limits
usernames to 32 characters in 2.4+, so the default `username_template` is
capped accordingly.

## Capabilities

| Plugin Name              | Root Credential Rotation | Dynamic Roles | Static Roles | Username Customization |
| ------------------------- | --------------------------- | --------------- | --------------- | ------------------------- |
| `milvus-database-plugin` | Yes                       | Yes            | Yes           | Yes                     |

## Setup

1.  Enable the database secrets engine if it is not already enabled:

    ```shell-session
    $ bao secrets enable database
    Success! Enabled the database secrets engine at: database/
    ```

    By default, the secrets engine will enable at the name of the engine. To
    enable the secrets engine at a different path, use the `-path` argument.

1.  Configure OpenBao with the proper plugin and connection information. The
    `url` must point at the Milvus HTTP endpoint:

    ```shell-session
    $ bao write database/config/milvus \
        plugin_name="milvus-database-plugin" \
        allowed_roles="reader" \
        url="http://milvus.example.com:19530" \
        username="root" \
        password="Milvus123"
    Success! Data written to: database/config/milvus
    ```

    Milvus also accepts a Zilliz Cloud-style API `token` in place of
    `username`/`password` — see the [API docs](pathname:///api-docs/secret/databases/milvus)
    for details.

1.  Configure a role that maps a name in OpenBao to a Milvus role-grant
    document to execute to create the database credential. The roles listed
    must already exist on the cluster:

    ```shell-session
    $ bao write database/roles/reader \
        db_name="milvus" \
        creation_statements='{"roles":["public"]}' \
        default_ttl="1h" \
        max_ttl="24h"
    Success! Data written to: database/roles/reader
    ```

## Usage

After the secrets engine is configured and a user/machine has an OpenBao token with
the proper permission, it can generate credentials.

1.  Generate a new credential by reading from the `/creds` endpoint with the name
    of the role:

    ```shell-session
    $ bao read database/creds/reader
    Key                Value
    ---                -----
    lease_id           database/creds/reader/2f6a614c-4aa2-7b19-24b9-ad944a8d4de6
    lease_duration     1h
    lease_renewable    true
    password           SsnoaA-8Tv4t34f41baD
    username           v-token-reader-x7g2kf8s1a-1717000000
    ```

## Milvus-specific notes

- **HTTP RESTful API v2, not the gRPC SDK**: The plugin talks to Milvus over
  its HTTP RESTful API v2 (`/v2/vectordb/users/...`), not the Milvus Go SDK
  or raw gRPC. `url` should be the base URL of that HTTP endpoint.
- **API-level errors return HTTP 200**: Milvus returns HTTP 200 with an
  envelope `{"code": N, "message": "..."}` even for failures. The plugin
  parses this envelope and treats a non-zero `code` as an error, so failures
  are never silently swallowed.
- **32-character username limit**: Milvus 2.4+ rejects usernames longer than
  32 characters. The default `username_template` is truncated to stay under
  this limit; if you supply a custom `username_template`, keep it within 32
  characters.
- **Partial-failure cleanup**: User creation and role grants are separate
  REST calls. If granting any role fails, the plugin drops the just-created
  user (`users/drop`) before returning the error, so no half-configured user
  is left behind.
- **Roles must pre-exist**: `creation_statements` only grants roles to the
  new user; it does not create roles. Any role named in
  `creation_statements` must already exist on the Milvus cluster.
